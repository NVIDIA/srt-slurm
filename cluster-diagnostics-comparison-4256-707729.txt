In Raplab the unrestricted local cases are 134.7-205.9 GiB/s versus 298.4-316.3
GiB/s when GPU-local CPU and memory binding is applied. Hecate unrestricted
local cases are 261.5-316.4 GiB/s. On Raplab, CPU submission is still about

unrestricted versus roughly 184-195 microseconds after binding. Thus the
observed bulk-copy gap is not explained by the measured CPU submission time
alone. The five samples generally reproduce the slower behavior within these
cases, but there is only one diagnostic job per cluster with a fixed test order.

Binding changes CPU affinity and memory policy together. The test cannot tell
which component matters, or separate allocator/cache/clock/order effects.
Furthermore, it uses one process sequentially across four GPUs and PyTorch can
reuse the same pinned allocation. Unrestricted buffer placement remains on
one NUMA node across those GPUs; it does not model four independent serving
ranks allocating GPU-local buffers. No tensor correctness check or serving
workload was performed, and clocks were only sampled around the test.

Connection to the current recipes and tekit

The Hecate c448 recipe has engine.numa_cpu_bind=true. The Raplab c448 recipe
omits it, giving the backend's default false. Both enable numa_memory_bind,
which produces numactl -m 0,1 and allows either memory node rather than ensuring
GPU-local allocation. This is a concrete configuration difference worth a
controlled serving comparison. Recipe settings alone do not establish actual
worker placement: tekit also has automatic affinity logic.

In tekit's configure_cpu_affinity, an inherited constrained mask and an unset
TLLM_NUMA_AWARE_WORKER_AFFINITY cause an attempt to remove constraints; that
branch does not then perform automatic GPU-local pinning. Explicit value 1
selects GPU-local affinity. A kernel cgroup CPU restriction still limits which
CPUs the process can use. The explicit srt-slurm wrapper instead disables
tekit's auto mode and taskset-binds per physical GPU before startup. Inspect
all-thread masks and pinned-page placement in the running workers before
concluding that either recipe actually has correct or incorrect placement.

Other observations confirmed in these new bundles

All four Python package lists and hashes of the three sampled TRT-LLM files
match. Raplab still uses GPU driver 620.47 / VBIOS 99.00.16.47.12; Hecate uses
620.43 / 99.00.16.47.0F. Both report Healthy/Full NVLink fabric and no route
recovery. CPU frequencies in these snapshots overlap around 3.3-3.4 GHz.

Raplab routes TCP through veth eth0 / 169.254.1.1; Hecate exposes physical and
IPoIB interfaces. Raplab's selected IB NICs span two reported subnets; Hecate's
span one. These are unchanged network differences, not newly proven causes.
Raplab NIC counters remain absent, preventing a transport-error/retry comparison.
Hecate has 604 readable numeric counters per host and no error/wait deltas in
this interval. Both diagnostic cgroups show zero CPU throttling and OOM events.
Idle snapshots do not exclude pressure or congestion during serving.

Next discriminating measurement

Check actual serving-rank CPU masks and pinned staging-page NUMA placement first.
Then compare identical serving runs with verified per-rank GPU-local affinity,
recording Mooncake queue wait, GET duration and host-to-GPU copy/sync duration,
along with cache-reused tokens/request and prefill-to-decode transfer time.
For a copy-only control, keep memory fixed on the GPU-local node and vary only
CPU affinity; run a fresh process per GPU and repeat/reorder the tests. Capture
clocks during the copies. That isolates the unrestricted-copy clue before
attributing it to NUMA scheduling, driver differences or network behavior.
